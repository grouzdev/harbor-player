# Блокеры выпуска: фокус Пульса и конкуренция SQLite

Источник: grouzdev в Delta разрешил разбор и исправление двух блокеров,
выявленных после отправки `ec71244`, с подготовкой `0.4.1-beta.3`.
Новый коммит в main и новый тег требуют отдельного подтверждения.
Существующие теги не перемещаем, релизные проверки не отключаем.

## Свидетельства и ожидаемый результат

- Release run `41214457154`: 560 модульных тестов прошли,
  Chrome 170/171, PageDown в Пульсе оставил фокус на ранге 0.
- Main CI `41214457334`: 559/560, у шести одновременных претендентов
  на владение каталогом не оказалось победителя.
- Локальный процессный прогон исходного кода: 100 раундов по 6 процессов,
  в одном раунде все шесть получили «уже запущен», хотя владельца не было.

Нужны детерминированные регрессии, устранение причин и полный gate.
Проверка Пульса должна покрывать отложенное монтирование уже загруженного
ранга без нового запроса данных. Проверка владения должна моделировать
краткий SHARED-reader SQLite, не являющийся владельцем сервиса.
Чужой живой владелец по-прежнему исключает претендентов; marker и ownership
database никогда автоматически не удаляются.

## Причины и исправления

В Пульсе список смонтированных рангов зависит от viewport, а эффект ожидающего
фокуса зависел только от ранга и загруженных данных. После скролла внутри
одной уже загруженной страницы эффект не повторялся. Добавлены зависимости
first/last: после появления DOM-узла запрос фокуса завершается.
Тест задерживает scroll-уведомление до первой попытки фокусировки, затем
разрешает монтирование; новых запросов artist-groups нет. На исходном коде
целевой ранг смонтировался, но оставался без фокуса; после исправления тест прошёл.

В SQLite timeout=0 превращал краткое присутствие SHARED-readers при открытии
в немедленный отказ всех процессов. Добавлен штатный busy timeout 1000 мс
и проверка journal_mode перенесена после BEGIN EXCLUSIVE. Отдельный тест
удерживает reader 150 мс: исходный код дал шесть отказов, исправленный —
одного владельца и пять отказов. Также проверен отказ для WAL без создания
marker и без изменения режима. Busy timeout — бюджет обработчика SQLite,
не жёсткий wall-clock предел: на Windows ожидание в отдельных прогонах
занимало около 1.8 с. Длительная конкуренция может по-прежнему завершиться
ошибкой; не вводится бесконечное ожидание, PID-takeover или удаление файлов.

## Результат локальной проверки

Подготовлена `0.4.1-beta.3` поверх `ec71244`, без коммита, тега и публикации.
Проверено на Windows, Node v24.20.0:

- `npm test` — PASS, 562 теста в 69 файлах.
- `npm run test:e2e` — PASS, Chrome 172/172, Edge 172/172.
- Целевые браузерные тесты cached-rank и 1000-rank с `--repeat-each=3`
  в Chrome и Edge — PASS, 12 запусков.
- Процессный стресс исходного/собранного кода, 100 раундов по 6 процессов:
  до исправления один раунд без победителя; после исправления все 100 раундов
  дали одного владельца и пять отказов, 600 процессов, около 187 секунд.
- `npm run desktop:dist` — PASS, NSIS и portable unsigned beta.3;
  включает typecheck, desktop build и production client build.
- `npm run test:desktop:smoke`, `npm run test:desktop:smoke:portable` — PASS.
- `node scripts/verify-release.mjs v0.4.1-beta.3 --channel=beta --artifacts` — PASS.
- `npm run lint`, Prettier изменённых TS/TSX и `git diff --check` — PASS.

Пользовательская БД и установленное приложение не менялись. Повторная проверка
remote CI и опубликованных файлов требует отдельного согласованного выпуска.
Реальная установка/переход beta.1 → beta.3 пока не проверены.
