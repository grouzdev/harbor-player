# Пульс: доказательства P0

## Область и среда

Выполнение [рабочего плана P0](../docs/pulse-p0-plan.md). Это журнал
проверок, не разрешение на релиз.

- Исходный HEAD: `b309473efda1764e439ed50340f8da6b2ee30009`.
- Среда: Windows, Node `24.20.0`, npm `11.19.0`.
- Изменения находятся в рабочем дереве; публикация/релиз не выполнялись.

## Подтверждённые причины и изменения

### E2e-блокеры каталога

Изменены тесты, не правила каталога:

- «Недавние» сразу применяется без автоматического редактора; явное
  редактирование остаётся отдельным сценарием.
- Topbar проверяет три самостоятельных действия: Пульс → обложка → fullscreen.
- Выбор артиста сохраняет upstream-библиотеку и очищает downstream-альбомы;
  ожидания согласованы с существующими unit-тестами.
- Cover mode переиспользует библиотеку по точному пути, не совпадению имени,
  и ожидает все семь треков нужной фикстуры.
- Bookmarks различает failed-load, loaded-empty и внешний reset. Исходное
  отдельное Edge-падение не воспроизвелось; состояние перед reset теперь явно
  проверяется. Individual/group и полный Edge успешны.

Каждый из пяти известных сценариев прошёл отдельно в Chrome и Edge;
группа `catalog-filters.spec.ts` + `library.spec.ts` — 34/34 в каждом браузере.
Unit selection/filter — 51/51. В изолированной копии требовался штатный
`npm ci` и `npm run verify:tags` (7/7), поскольку локальный package.json
taglib отсутствовал: защита корректно оставляла FLAC read-only.
Сгенерированные изменения `verification/tag-support.json` не включены в diff.
Skip/retries/исключения и увеличение существующих timeout не добавлялись.

### Локальная запись и общий outbox

- Раньше ошибка `PulseOutbox.put()` только сообщалась: событие, закрытое
  recorder, больше не удерживалось для повторной записи. Теперь последняя
  накопительная ревизия удерживается в памяти до успешной транзакции или
  признания старого поколения; `pending()` повторяет запись перед доставкой.
- Ошибка открытия IndexedDB раньше оставляла навсегда rejected Promise.
  Открытие теперь ленивое, неуспешное подключение можно повторить.
- `reconcile()` раньше безусловно записывал переданное поколение и удалял
  несовпадающие события. Поздний ответ настроек старого окна мог стереть
  pending нового поколения. Теперь поколение общего outbox не уменьшается;
  delivery перечитывает устаревшие настройки.
- Настройки, изменённые во время выполняющегося flush, теперь запрашиваются
  повторно после него. BroadcastChannel сообщает об изменении соседним
  окнам, в том числе остановленным и с пустым outbox.
- При изменении настроек recorder закрывает текущий участок и ждёт свежих
  настроек. Поздний ответ более раннего запроса не возобновляет сбор.
- Успешный отдельный `put()` не скрывает прежнюю ошибку доставки; успешное
  восстановление idle-хранилища снимает ошибку без фонового опроса API.

Независимый review выявил ещё один порядок `1 → POST response 2 → GET 3`.
Все fresh settings теперь проходят единый GET/reconcile-путь перед применением
к recorder; новая ревизия generation 3 не теряется при несовпавшей meta.
Для этого добавлена отдельная детерминированная регрессия.

Целевой browser-прогон:

```sh
npx playwright test tests/browser/pulse-outbox.spec.ts tests/browser/pulse-reliability.spec.ts --project=chrome
npx playwright test tests/browser/pulse-outbox.spec.ts tests/browser/pulse-reliability.spec.ts --project=edge
```

**12/12 в каждом браузере.** Проверены idle на нескольких flush ticks,
reload с durable pending без playback, commit с потерянным ACK,
поздний ACK при новой ревизии, старое окно/new generation, IDB open/abort/quota
и восстановление ошибки UI. Гонка POST/clear проверяется отдельно в одном
окне для обоих серверных порядков; второе окно не может случайно завершить
доставку вместо проверяемого окна. Broadcast проверяется отдельно при пустом outbox.

С настоящим 40-секундным WAV отказ `/listening-events` удерживает checkpoint;
после восстановления он доставляется. Disable не останавливает аудио, но
не меняет подтверждённую статистику; после enable новое поколение начинается
не раньше момента включения. Итоговая сумма API равна сумме последних
успешно принятых ревизий. Это отказ HTTP, не остановка процесса сервера.

Серверная fault-регрессия внедряет write failure на втором событии батча:
HTTP 500 без ACK, все интервалы/агрегаты/aliases первого события откатываются;
после устранения ошибки retry и duplicate дают ровно 30 000 мс.

**Предел:** память после неуспешной записи не является долговременным
хранилищем. Закрытие окна при недоступной IndexedDB может потерять данные.
Периодический checkpoint ограничивает хвост примерно 15 секундами только
при исправной локальной записи и своевременном выполнении checkpoint;
`pagehide` остаётся best effort.

### HTTP и миллисекунды

`toPulseEvent()` — общий проверяемый путь преобразования recorder → HTTP.
Семантика не изменена: floor UTC-границ и накопленного `playedMs`, финальная
ревизия может не добавлять целую миллисекунду. Интервал целиком < 1 мс
recorder не публикует; дробная часть теряется при квантовании.

`npm run build && npx vitest run tests/pulse-recorder.test.ts tests/pulse-time.test.ts`:
успешно, **29 тестов**. Проверены 0,5×/1×/2×, checkpoint/final/stale retry,
seek в обе стороны, события аудио через адаптер, delayed sample > 3 часов,
часовые границы и единый visitId, скачки wall-clock, фактические DST-переходы
Нью-Йорка и сохранённая timezone после смены `TZ` процесса.

Через настоящий `createApp`/HTTP inject/SQLite подтверждено:

`Σ latest intervals.playedMs = Σ days.playedMs = Σ day_albums.playedMs = Σ album_stats.playedMs`.

### Сохранность каталога и миграция

Ошибка `mkdirSync`/`copyFileSync` исторической обложки воспроизведена
регрессией: ingest падал до записи времени. Копирование теперь best effort;
имя, snapshot и время сохраняются, отсутствие изображения допускает fallback.
HTTP-проверки подтверждают историческую обложку после удаления текущего кэша
(200) и отсутствующую/несохранённую обложку (404).

`npm run build:server && npx vitest run tests/pulse.test.ts tests/pulse-migration.test.ts`:
**22/22**, включая:

- реальные операции Catalog: rename библиотеки, upsert новых тегов,
  filesystem rename/upsert перемещения, removeLibrary, reopen;
  прежние albumId, aliases, snapshot и 45 000 мс остаются;
- ingest → clear и clear → старый ingest, restart и новое поколение;
- независимые sessions, retry и final без прироста: 30 000 мс и два визита.

Миграционная фикстура создана **настоящим старым Catalog** из
`72403c6c820d0f81cf071db135105e00638f81f8` (родитель первого Pulse/v13-коммита).
Старые исходники экспортируются и компилируются внутри `.test-data`;
вымышленные библиотека/трек/плейлист/очередь записываются старым приложением.
Никакого понижения `user_version` новой БД нет.

Подтверждены v12 → v13, все каталожные строки и схема без изменений,
integrity/FK, чтение playlist/queue и повторное открытие.
Fault после фактического исполнения v13 DDL внутри транзакции сохраняет
v12 без частичных Pulse-таблиц; повторный запуск успешно мигрирует.

**Граница доказательства:** это synthetic old-code fixture, не пользовательская
БД и не прогон scanner/tag-editor/UI. Для запуска migration-теста нужен
указанный Git object; shallow checkout должен предварительно получить его.
