# Пульс: рабочий план P0

Детализация [P0 финализации](pulse-finalization-plan.md#p0--закрыть-до-релиза).
Это план работ, не отчёт об успешных проверках. Исходные результаты прогонов
сохранены в финализации; здесь они не объявляются повторно подтверждёнными.
Фактические результаты выполнения и оставшиеся ручные проверки:
[журнал P0](../verification/pulse-p0.md).

## Решение и порядок

Закрывать P0 отдельными проверяемыми изменениями, без переписывания каталога,
нового дизайна и функций P2:

1. Подготовить изолированные данные и журнал доказательств.
2. Исправить известные e2e-блокеры и добавить idle/restart-регрессию.
3. Зафиксировать учёт целых миллисекунд от recorder до HTTP и агрегатов.
4. Закрыть сбои доставки, хранения и гонки поколений.
5. Проверить настоящую миграцию и независимость истории от каталога.
6. На итоговом состоянии выполнить полный gate P0.

Шаги 2 и 5 можно вести независимо. Шаг 3 предшествует сверке итогового времени
в шаге 4: без общего правила округления сравнение будет неоднозначным.
Миграционный артефакт нужно получить сразу, не откладывать до финального gate.
Полный e2e полезно запускать после шага 2 для поиска оставшихся блокеров,
но приёмочным будет повторный полный прогон после всех исправлений.

## 0. Подготовка и доказательства

- [ ] Подтвердить среду: Node 24, зависимости проекта, установленные Chrome и
  Edge, возможность запуска Electron для crash/restart и нескольких окон.
- [ ] Сверить `playwright.config.ts`, общий сервер, каталог фикстур и состояние
  SQLite. Новый browser context не означает новую серверную БД.
  Сейчас `workers: 1`, а `scripts/e2e-server.mjs` пересоздаёт
  `.test-data/browser` при каждом запуске Playwright. Пути аудиофикстур
  разделены по браузеру/сценарию, но `dataDir` общий внутри одного прогона.
  Chrome и Edge запускать последовательно, не параллельно на одном порту.
- [ ] Для новых сценариев давать уникальные имена/пути библиотекам и событиям;
  явно устанавливать settings/generation. Очистка тестовых данных не должна
  уничтожать пользовательскую историю или каталоги.
- [ ] Подготовить копию БД, действительно созданной версией v12, с библиотекой,
  плейлистом и очередью. При живой SQLite использовать согласованный backup,
  а не отдельно копировать основной файл без учёта WAL.
- [ ] Завести `verification/pulse-p0.md`: окружение, версия кода, команда,
  результат, ссылки на trace/логи, найденная причина и способ исправления.
  Для ручных проверок — шаги и фактические значения до/после.

**Входной блокер:** если реальной БД v12 нет, запросить у разработчика её
локальную копию либо получить её запуском приложения из настоящей версии v12.
Не публиковать личную БД в Git; для автоматизации подготовить безопасную
фикстуру из старой версии с документированным происхождением.

## 1. E2e: исправить причины, не ожидания ради зелёного цвета

Область: `tests/browser/catalog-filters.spec.ts`, `library.spec.ts`,
bookmark-сценарий, общие helpers и текущие правила каталога.

- [ ] Воспроизвести каждый известный сбой отдельно в Chrome и Edge,
  затем вместе с соседними сценариями. Сохранить trace при падении.
- [ ] Для «Недавние» сверить контракт добавления фильтра с реализацией:
  должен ли редактор открываться сразу? Если нет — убрать устаревшее ожидание
  закрытия редактора; открытие для редактирования проверять отдельным действием.
  Если да — исправлять приложение и добавить регрессию.
  Уже подтверждено противоречие: соседний тест
  `recent filter applies its period immediately` ожидает отсутствие редактора
  после добавления и открывает его отдельным кликом.
- [ ] Проверить topbar: Пульс и обложка — отдельные кнопки, порядок контролов
  соответствует текущему UI; не объединять их ради старой проверки.
- [ ] В сценарии local library сверить выбор артиста с сохранением
  upstream-контекста. Менять ожидание только после подтверждения правила,
  покрытого существующими тестами выбора/фильтрации.
- [ ] Для cover mode устранить конфликт библиотек на общем сервере:
  уникальная фикстура либо явное использование уже подключённой библиотеки.
  Не закрывать зависший диалог вслепую — подтвердить подключение и завершение scan.
  Сейчас поиск использует имя `Downloads <project>`, а путь —
  `<project>/cover-mode/Downloads`: наличие одноимённой библиотеки не доказывает,
  что она указывает на нужную фикстуру. Сверять также путь/идентичность.
- [ ] Для Edge/bookmarks различить ошибку загрузки, успешно пустой ответ и
  внешний reset. Проверить «Показать всю музыку» в предназначенном для него
  состоянии; retry и reset должны восстанавливать именно нужное состояние.
- [ ] Добавить browser-регрессию интеграции `usePlayer`:
  остановленный `<audio>` и пустой outbox не инициируют запросы истории
  после нескольких периодов flush; pending после reload доставляется даже
  без запуска аудио. Считать запросы history/settings отдельно от каталожных.

**Закрытие:** сценарии проходят по одному и в группе в обоих браузерах;
для каждой правки записана причина — дефект приложения, устаревший контракт
теста или неизолированная фикстура. Не добавлять skip, grep-invert,
увеличение timeout или retries для сокрытия причины.

## 2. Время: один контракт на всех границах

Точки: `src/client/pulse-recorder.ts`, преобразование событий в
`src/client/Player.tsx`, HTTP-валидация и агрегаты `src/server/pulse.ts`.
База проверок: `tests/pulse-recorder.test.ts`, `tests/pulse.test.ts`.

Уже есть тесты 2×, seek/stall, pause, повторов, смены скорости, часовых частей
и задержанного sample. Серверные тесты проверяют целые миллисекунды и полночь.
Они не заменяют проверку всей цепочки recorder → HTTP → SQLite.

- [ ] Таблица детерминированных сценариев: 1×/0,5×/2×, seek в обе стороны,
  repeat-one, pause/resume, waiting/playing, error, смена source при файловой
  операции. Метрика — реальное время подтверждённого playback, не длина аудио.
- [ ] Проверить субмиллисекундные sample и checkpoint/final с одинаковым
  округлённым временем. На HTTP отправлять целые UTC/playedMs; финальная ревизия
  может не прибавлять время. Ни одна ревизия не уменьшает принятую сумму.
- [ ] Зафиксировать правило для интервала с итогом < 1 мс: он не представим
  положительным целым `playedMs`. Документировать квантование, не отправлять
  нулевой интервал и не обещать точность меньше миллисекунды.
- [ ] Проверять сумму последних принятых ревизий, а не всех checkpoint:
  `Σ playedMs интервалов = Σ pulse_days.playedMs = Σ pulse_album_stats.playedMs`.
  Также сверить дневные вклады альбомов, уникальные визиты и отсутствие
  отрицательного прироста. Проверять не только UI, округляющий минуты.
- [ ] Проверить несколько часов и один большой delayed sample:
  каждый участок ≤ 1 часа, продолжения сохраняют visitId.
- [ ] Проверить фактический DST-переход вперёд и назад, а не только полночь
  даты перехода; сохранённый timezone, смену системной зоны и wall-clock.
- [ ] Ручной прогон настоящего audio: фон, throttling таймеров, sleep/wake.
  Продвижение считается, сон без продвижения — нет. Записать наблюдаемые
  события и суммы; не эмулировать все события только вызовами recorder.

**Закрытие:** все состояния имеют ожидаемое время и идентичность визита;
после HTTP-квантования суммы сходятся точно в целых миллисекундах.

## 3. Надёжность: доставка и ошибки хранения

Точки: `PulseOutbox`/`PulseDelivery` в `src/client/pulse-outbox.ts`,
жизненный цикл recorder и status в `Player.tsx`, generation/ingest на сервере.
База browser-проверок: `tests/browser/pulse-outbox.spec.ts`, `pulse.spec.ts`.

Существующий outbox-тест проверяет coalescing, поздний ACK, stale generation
и backoff через подставной transport. Следующие проверки должны дополнить его,
а не повторить только тот же путь.

| Сценарий | Воздействие | Доказательство |
| --- | --- | --- |
| Сервер недоступен | Во время playback остановить только тестовый API, пройти несколько треков/checkpoint, затем восстановить | Pending сохраняется; после доставки последняя ревизия каждого eventId принята один раз; суммы сходятся |
| Commit без полученного ACK | Принять POST сервером, оборвать ответ, повторить доставку | Retry не удваивает время/визиты |
| Restart с pending | Reload/перезапуск на том же origin и профиле с IndexedDB | Без playback outbox доставляется; новое приложение не дописывает время простоя |
| Crash после checkpoint | Дождаться завершения локальной транзакции, аварийно закрыть тестовое окно | Сохранённый checkpoint остаётся; измерен потерянный хвост, около 15 с только при исправной записи и своевременном checkpoint |
| Clear во время POST | Управляемым барьером задержать запрос или ACK, записать более новую pending revision, очистить, отпустить барьер | Ни поздний ACK, ни старый POST, ни restart не восстанавливают старое поколение; новое поколение принимается |
| Disable/enable во время playback | Отключить сбор, продолжить аудио, включить | Нет времени выключенного периода; прежняя эпоха не импортируется скрыто |
| Несколько окон | Два окна одного профиля, rerender/mount и два реальных playback | Один recorder на audio; независимые sessionId считаются отдельно; общая доставка не дублирует суммы |

- [ ] Для гонок проверить оба порядка серверной обработки: ingest до clear
  и clear до ingest. Задержка только клиентского ответа не моделирует оба случая.
- [ ] Ввести управляемую инъекцию ошибок открытия IndexedDB, abort/write/quota
  и серверной записи на диск. Реальный диск пользователя не заполнять.
- [ ] Проверить видимую ошибку и восстановление: pending не ACK-ается без
  успешной записи; ошибка исчезает после восстановления, повторные ошибки
  не создают бесконечные уведомления.
- [ ] Отдельно выяснить судьбу события при неуспешном `outbox.put()`:
  уведомление само по себе не доказывает сохранность. Если событие теряется,
  исправить удержание/повтор записи в рамках P0; память не выдавать за durable
  гарантию при crash и недоступной IndexedDB.
- [ ] Сверить правила общей IndexedDB и локальных settings разных окон,
  включая clear/disable в соседнем окне и позднюю доставку.

**Закрытие:** суммы и визиты сходятся после всех допустимых перестановок;
отказ долговременного хранения явно виден и его пределы документированы.
Управление единственным активным playback между окнами остаётся P2.

атомарна; lifecycle каталога и изображений не уничтожает историю.

## 5. Итоговый gate P0

Перед целевыми Vitest-проверками сервер нужно собрать, поскольку тесты
импортируют `dist/server`. Для диагностики:

```sh
npm run build:server
npx vitest run tests/pulse-recorder.test.ts tests/pulse.test.ts
npm run build
npx playwright test tests/browser/catalog-filters.spec.ts tests/browser/library.spec.ts --project=chrome
npx playwright test tests/browser/catalog-filters.spec.ts tests/browser/library.spec.ts --project=edge
npx playwright test tests/browser/pulse-outbox.spec.ts tests/browser/pulse.spec.ts --project=chrome
npx playwright test tests/browser/pulse-outbox.spec.ts tests/browser/pulse.spec.ts --project=edge
```

Новые тесты включить в соответствующие целевые команды. После всех изменений
выполнить без фильтров и исключений:

```sh
npm test
npm run build
npm run lint
npm run format:check
npm run test:e2e
git diff --check
```

`npm run test:e2e` запускает Chrome, затем Edge через `&&`: при падении Chrome
Edge не запускался. Диагностический отдельный запуск Edge допустим, но не
заменяет итоговый успешный запуск точной команды.

- [ ] В журнале есть результаты автоматических и ручных проверок всех четырёх
  пунктов исходного P0, а не только зелёный Playwright.
- [ ] Старые нарушения format отделены от новых; новые устранены.
- [ ] Чекбоксы финализации отмечены только по фактическим доказательствам.
- [ ] Ограничения записи, квантования и crash-потерь описаны без обещания lossless.

Закрытый P0 ещё не разрешает релиз: проверки UI/скорости P1 и финальный gate
из исходного документа остаются обязательными. Публикация — отдельное действие.
