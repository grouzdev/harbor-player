# Пульс: рабочий план P1

Детализация [P1 финализации](pulse-finalization-plan.md#p1--закончить-проверку-интерфейса-и-скорости).
Это план реализации и приёмки, не отчёт о выполнении. Чекбоксы P1 в финализации
остаются единственным сводным статусом; отмечать их только по новым результатам.
Физический sleep/wake остаётся отдельным незакрытым P0.

## Результат и границы

Получить проверенный интерфейс Пульса в браузерах и установленном Windows
Electron, измерить полный путь от пользовательского действия до готового экрана,
исправить обнаруженные причины отклонений и записать доказательства.

- Не переписывать самостоятельный режим обложки и правила каталога.
- Не добавлять статистику дня/периода, новые переключатели дизайна и функции P2.
- Не менять recorder, delivery и схему БД ради ускорения UI без доказанной причины.
- Все очистки, synthetic seed и нагрузочные записи — только в собственных
  `.test-data/pulse-p1-*`, с отдельными БД, origin и Electron profile.
  Единственную рабочую v13 не очищать и не наполнять тестовыми интервалами.
- Реальные обложки брать из локальных разрешённых материалов; содержимое
  пользовательской библиотеки и профили с частными данными не публиковать.
- Установка/обновление приложения на целевом ПК требует отдельного согласования.
  Packaged `win-unpacked` полезен для автоматизации, но не заменяет требуемую
  ручную проверку установленного приложения.

## 1. Подготовить воспроизводимые данные и журнал

Создать `verification/pulse-p1.md` с таблицей:
сценарий → сборка/окружение → команда или ручные шаги → результат/числа →
локальный evidence → дефект/повторная проверка. Пока прогонов нет — `NOT RUN`.

Подготовить общий seed для новых UI-тестов и benchmark harness, не копируя
действующую БД. Небольшие UI-фикстуры вводить через реальный API с проверкой
ACK; bulk dataset допустимо строить напрямую в disposable SQLite по примеру
read-benchmark, но не использовать такой seed как доказательство ingest.

Наборы:

1. Пусто: collection enabled/disabled; существующая история при disabled.
2. Обычная история: несколько дней/альбомов, выбор не последней карточки.
3. Десять календарных лет: активные и пустые дни, разные размеры дней,
   отдельный день ровно с 1000 альбомами и известным порядком/суммами.
4. Длинные title/artist, отсутствующие и повреждённые обложки; реальные
   изображения разного размера/разрешения с записанным распределением.
5. Ошибки history/layout/pages/stats, задержанные ответы в обратном порядке,
   clear при выполняющемся запросе. Mock только для воспроизводимой ошибки;
   основной путь всегда проходит реальный API.

Сохранять seed/version и manifest ожидаемых значений. Нагрузочную фикстуру
не гонять заново во всех вариантах размеров/тем: отдельный stress suite,
небольшие данные для основной визуальной матрицы.

**Выход:** изолированные данные, сценарии и формат отчёта готовы.

## 2. Shell, состояния и доступность

Расширить `tests/browser/pulse.spec.ts`; общие helpers вынести только при
реальном повторном использовании. Исправлять соответствующий слой shell,
Dialog или PulseMode, не вводить второй независимый механизм hotkeys/focus.

- Переходы panels → pulse → panels, pulse → cover → pulse, общие настройки
  → возврат; отдельно кнопка и Escape. Сохраняются playback/src/queue,
  каталог, его scroll и допустимый фокус. Возврат проверять и после удаления
  исходного focus target: нужен подключённый видимый fallback.
- Native Tab/Shift+Tab в Пульсе и модальном диалоге, видимый focus ring,
  доступные имена кнопок/range/cards. Hidden/inert каталог не получает
  фокус и каталоговые hotkeys; документированные player hotkeys сохраняются.
- Escape закрывает только верхний активный диалог, не одновременно Пульс;
  после закрытия фокус возвращается к открывшей кнопке.
- Повторный вход восстанавливает date + offset + selected day/album и
  актуальную статистику. Проверить также clear, пока Пульс не смонтирован:
  старая selection не должна воскреснуть из shell state.
- Clear при in-flight stats/pages: старый ответ не возвращает карточку,
  статистику и старое поколение; playback/каталог остаются нетронутыми.
- Disabled не скрывает уже собранную историю; empty/disabled/loading/error
  не смешиваются. Retry действительно восстанавливает данные и снимает ошибку.
  API/cover 404 не убирает название, время и доступность карточки.

**Приёмка:** все перечисленные состояния имеют assertions, не только скриншоты;
прогон Chrome + Edge. Уже существующие сценарии не объявлять новым покрытием.

## 3. Виртуальная лента и ввод

Отдельный stress сценарий на 1000 альбомах:

- Мышью добраться до первой/средней/последней карточки и сверить ID/rank.
- Клавиатурой пройти границу виртуальных страниц и выбрать крайние карточки
  без мыши, программного scroll/evaluate и прямого focus на невидимый DOM.
  Удержание старого focus само по себе не доказывает достижимость следующего.
- Проверить Tab/Shift+Tab, Enter/Space, rail Arrow/Home/End/PageUp/PageDown,
  range; смену viewport при сфокусированной карточке и уход за её границы.
  Если выявится разрыв навигации, выбрать один согласованный механизм
  навигации по логическому rank с загрузкой/scroll/focus, сохранив native Tab
  между контролами. Не рендерить 1000 кнопок как обход виртуализации.
- Mouse drag с отпусканием вне rail; `pointercancel`/`lostpointercapture`:
  drag-state снимается, следующий drag работает, случайный select не возникает.
- Wheel deltaX/deltaY и pixel/line/page, начало/конец; Ctrl+wheel не перехватывается.
  Синтетический WheelEvent доказывает только обработчик: масштабирование,
  инерцию trackpad и touch-pan дополнительно проверить реальным вводом.
- Быстрые переходы range между годами и возврат: отменённые pages/stats/layout
  не меняют итоговую дату/selection; clear сильнее старых ответов.

**Приёмка:** все 1000 достижимы без потери фокуса; DOM зависит от viewport +
overscan + удержанного focus, а не размера истории/дня.

## 5. End-to-end измерения до оптимизаций

Добавить `scripts/pulse-ui-benchmark.mjs` и предлагаемую команду
`test:pulse:ui` для production build + собственного процесса/профиля.
Переиспользовать принципы изоляции desktop harness, не crash-сценарии.
Сохранять samples/summary, network counts, DOM counts и trace в
`.test-data/pulse-p1-*`. Браузер полезен для диагностики; итоговые бюджеты
проверять на целевом Windows Electron без dev server и React dev mode.

### Метрики и протокол

- Начало — реальный click/keyboard activation переключателя.
- `shellReady` — первый paint нужного shell; `dataReady` — layout, видимые
  cards и выбранная статистика; `coversReady` — видимые обложки загружены
  и декодированы (ошибка явно учтена), затем следующий paint.
- Для возврата к панелям — видимые прежние панели, scroll и восстановленный
  focus на следующем paint. Одного `toBeVisible()` для latency недостаточно.
- Cold: первый вход после нового процесса с холодными module/HTTP/profile
  caches; каждый sample — отдельный запуск. Это не обещание холодного OS
  filesystem cache. Не чистить общесистемные кэши.
- Warm: повторный вход в том же процессе после готового экрана; отдельно
  immediate, после TTL > 30 с, после новых listening events и clear.
  Не называть повторный read SQLite «тёплым открытием UI».
- На обычном и десятилетнем наборе: минимум 10 cold и 30 warm/return samples,
  median/p95/max, число HTTP/bytes, раздельно обложки.
  Окружение/другую нагрузку ПК зафиксировать.
- Ориентиры финализации: warm/return < 100 мс, cold < 300 мс, read p95 < 50 мс.
  Для прозрачной оценки сравнивать p95 `dataReady`, показывать также
  `shellReady`/`coversReady`; не выдавать быстрый skeleton за готовый экран.
  Малое число cold samples отметить как ограничение статистики.

### Навигация, DOM, cache и память

Воспроизводимый профиль: drag, wheel и range-прыжки по десяти годам,
затем 30 минут навигации с повторением тех же точек.
PerformanceObserver longtask + Chromium trace: максимальная задача,
число > 50 мс, frames и причина; чистые latency-прогоны отдельно от
тяжёлого профилирования. По ориентиру финализации long task > 50 мс
во время прокрутки требует разбора и исправления причины.

Записывать live дни/cards/images, pending requests и запросы по endpoints.
Проверить page requests ≤ 100 элементов, отсутствие полной загрузки busy day,
повторную навигацию внутри страницы и отмену уходящих запросов.
Проверить LRU ≤ 24/16 и TTL unit-тестами API adapter; при необходимости
минимально выделить cache helper, не создавать production telemetry API.
Layout metadata могут зависеть от числа дней, DOM и карточные кэши — нет.

JS heap и память renderer измерять до нагрузки, на плато и после idle;
heap snapshots сравнивать после одинакового GC только в диагностическом
прогоне. Image/GPU memory не считать покрытой одной метрикой JS heap.
Искать удержанные mounted days/cards/requests и монотонный рост на
повторении одинакового маршрута, не требовать возврата RSS байт-в-байт.

### Что менять только после evidence

Если latency упирается в повторную загрузку десяти последовательных layout
окон — рассмотреть bounded metadata cache/ограниченный parallel read,
с корректной invalidation по listening/settings/generation и abort.
Если проблема в paint — уменьшить лишние renders/пересчёты.
Если decode/transfer оригиналов доминирует — использовать существующий
thumbnail путь, если он есть; иначе отдельно спроектировать производные
миниатюры без потери исторического оригинала и без политики GC из P2.
Каждое исправление сопровождается регрессией и тем же повторным замером.

## 6. Сервер: reads, ingest и рост данных

Повторить точную команду из финализации:

```sh
npm run build:server && node scripts/pulse-benchmark.mjs
```

Сохранить полный JSON, query plans и окружение. Этот benchmark сам удаляет
disposable БД; его результаты относятся к SQLite + JSON после seed/ANALYZE,
не к HTTP, UI, реальной частоте playback или времени ingest.

Добавить отдельный `scripts/pulse-ingest-benchmark.mjs`:

- Реальный HTTP ingest: 1, 20 и разрешённый максимум 100 событий;
  новые интервалы, checkpoint revisions, final, повторная доставка.
- Измерять отдельно validation, sync filesystem artwork work до транзакции,
  собственно SQLite transaction/commit и полную HTTP latency.
  Прогон с уже имеющимися и впервые копируемыми обложками.
- В другом клиенте параллельно выполнять обычные запросы каталога на
  фиксированной библиотеке: baseline и под ingest, median/p95/max,
  server event-loop delay и максимальное непрерывное блокирование.
  Запросы из одного клиента не должны случайно сериализовать нагрузку.
- Сверять точные raw/day/day-album/stats суммы после нагрузки и неизменность
  сумм при retries. Недопустимо ускорять запись потерей ACK/durability.
- Read p95 сравнить с 50 мс. Для ingest записать фактическую блокировку
  и ухудшение каталога; отдельного transaction-бюджета в финализации нет.
  Если пользовательские запросы заметно деградируют — исправить узкое место
  и повторить; не объявлять его допустимым только по быстрому read baseline.

Рост измерять через настоящий ingest по cadence recorder (checkpoint ~15 с,
новые revision одного eventId, финал трека, части долгого интервала),
а не миллион независимых строк вместо обычных ревизий.
Задать и записать модель: например, 2 ч/день, треки 3–5 минут,
разные доли новых/повторных альбомов и уникальных обложек.
Отдельно фактический короткий playback прогон и ускоренная модель
30/365 дней; годовую экстраполяцию не выдавать за год наблюдений.

Замеры: intervals/albums/day aggregates, размеры raw/index через `dbstat`
при доступности (иначе явно отметить отсутствие раздельных чисел),
SQLite и WAL до/после checkpoint, peak WAL и реальные bytes/count
`pulse-covers`. Контролируемый checkpoint только в тестовой БД.
Не вводить retention/компактацию/удаление обложек в рамках P1.

## Порядок реализации и финальная приёмка

1. Отдельный CI fix и Windows verify.
2. Общие изолированные данные + журнал; baseline UI/server измерения.
3. Shell/states/focus регрессии и минимальные исправления.
4. Virtualized keyboard/input и responsive matrix.
5. UI/ingest harness, stress/navigation/memory/artwork profiles;
   исправления только по найденным причинам с повторным baseline.
6. Свежая установленная сборка: ручные сценарии и целевые бюджеты.
7. Запись результатов и сводные отметки в финализации.

UI-регрессии и серверный measurement harness можно разрабатывать независимо
после согласования seed/evidence. Финальную ручную проверку выполнять
после последнего изменения, иначе она относится к другой сборке.

После последнего исходного изменения:

```sh
npm test
npm run build
npm run lint
npm run format:check
npm run test:e2e
git diff --check
```

Полный `test:e2e` — Chrome + Edge без фильтров/skip; targeted tests полезны
при разработке, но не заменяют gate. Format baseline перепроверить:
не переносить старое число нарушений в новый отчёт без фактического прогона.
Выполнить новые harness-команды после их реализации и точный read-benchmark.
Если затронуты ingest, recorder/delivery/lifecycle — повторить
`test:pulse:process` и `test:pulse:desktop`; изменение sleep-учёта также
требует релевантной P0-проверки, а не нового заявления по unit tests.

P1 закрывается только при наличии UI browser evidence, установленного
Electron checklist и performance/storage отчёта с объяснёнными отклонениями.
Недоступные ручные проверки остаются открытыми. Даже закрытый P1 не закрывает
физический sleep/wake P0 и не разрешает релиз/публикацию автоматически.
