# Пульс: план закрытия оставшихся релизных работ

Актуализация [финализации](pulse-finalization-plan.md) после
[четвёртого этапа](../verification/pulse-p1-stage4.md).
База планирования — `00f9342f98086f553a0b6bbf21371da848f9d106`,
ветка `wip/pulse-p1-followup`. Это план, а не новый результат проверок.
При исполнении записывать фактическую версию исходников и сборки.

## Границы и порядок

P0 закрыт. Не повторять поиск пользовательской v12, физический sleep/wake,
eager/lazy A/B и два принятых 30-минутных memory cohort без релевантных изменений.
Foreground cold guide уже подтверждён; исторический Edge startup хвост
не объяснён и не считается исправленным. Старые D1–D5 в
[плане доработок](pulse-p1-followup-plan.md) — контекст, не список работ с нуля.

Критический путь:

1. **R1: исключительное владение data dir → R2: owned-staging recovery.**
2. **R3: недостающие UI-профили и Edge-диагностика.**
3. **R4: permitted artwork и actual storage.**
4. **R5: установленная сборка и ручная приёмка.**
5. **R6: финальные проверки и CI на согласованном SHA.**

R3 и подготовку R4 можно вести независимо от R1–R2; окончательные storage
измерения делать после recovery. R5 — на сборке с принятыми исправлениями.
Каждый пункт — отдельная обозримая задача с результатом и пределами проверки,
не одна большая переработка. Сроки оценивать после выбора ownership-протокола
и согласования доступного оборудования/изображений.

Не менять рабочую v13, пользовательский профиль, часы и power settings.
Все автоматические прогоны — на собственных изолированных данных.
Не добавлять P2, retention/GC опубликованных обложек, новые режимы дизайна
или схему БД. Установка, push, интеграция с `main` и релиз требуют отдельного
явного действия пользователя.

## R1. Безопасное исключительное владение каталогом данных

**Проблема:** `src/server/instance-lock.ts` раздельно читает старый PID и
удаляет lock; конкурентный рестартер может удалить уже новую блокировку.
Проверка token при release сама по себе не решает stale takeover.

- Сначала создать воспроизводящий multi-process тест: два претендента
  встречают один stale lock; в критических точках синхронизировать процессы
  барьерами, а не надеяться на случайный timing.
- Сравнить системную блокировку, автоматически освобождаемую при смерти
  процесса, и файловый протокол с доказуемо эксклюзивным takeover.
  Рекомендация — системная блокировка, если совместимость с Windows,
  Electron/Node и целевыми файловыми системами подтверждена. Дополнительную
  native-зависимость или ограничение файловых систем согласовать до реализации.
  Не заменять гонку новым stale-файлом с такой же гонкой.
- Проверить live owner, одновременный старт, crash владельца, crash во время
  takeover, ошибку доступа, повреждённую/неполную запись, поздний release
  прежнего владельца и повторный release. Неопределённость — отказ от takeover,
  а не разрешение удалить lock и продолжить.
- Проверить lifecycle `MusicService`: ресурсы открываются только после
  владения, освобождение не затрагивает нового владельца.

**Приёмка:** один действующий владелец; проигравший не открывает БД для работы,
не удаляет lock победителя и не запускает recovery. Реальный concurrent
process/crash прогон дополняет детерминированные тесты.
Если безопасный takeover пока недоступен, остановиться: R2 остаётся блокирован,
опасный автоматический cleanup не включать.

## R2. Консервативный owned-staging recovery

Точки: `src/server/pulse.ts`, lifecycle `MusicService`,
`scripts/pulse-publication-crash-check.mjs` и storage/API тесты.

- Запускать recovery только под подтверждённым владением R1, до новых copy.
- Удалять только однозначно собственные staging-каталоги точного формата.
  Foreign/ambiguous entries, symlink/junction, flat/archive и опубликованные
  изображения сохранять. Одного mtime или PID недостаточно.
- Ограничить retries transient sharing-errors; постоянную ошибку отражать
  диагностикой. Не создавать бесконечный фоновый GC.
- Расширить `npm run test:pulse:publication`: настоящий kill во время partial
  copy → restart → cleanup → retry; повторить несколько циклов и проверить
  отсутствие накопления orphan. Сохранить foreign/published canaries.

**Приёмка:** нет partial publication и раннего ACK; архив совпадает с source
по hash; retry даёт точные суммы без дублей; удаляются только owned orphan.
Проверка физического FAT/exFAT выполняется при наличии разрешённого тестового
носителя; симуляция остаётся отдельным результатом, не physical PASS.

## R3. Завершить UI/performance evidence

Точки: `scripts/pulse-ui-benchmark.mjs`, `pulse-ui-evidence.mjs`,
`pulse-ui-options.mjs`, browser-регрессии и, только при доказанной причине,
production UI.

- Составить покрытие незакрытых пунктов §5 финализации: режимы/диалоги,
  focus/scroll restore, невидимые панели, empty/disabled/API/cover errors,
  длинные названия, размеры 390/640/800/1366/1600 px и низкое окно.
  Использовать существующие тесты; добавлять только недостающие регрессии.
- Записать отдельные drag/wheel/year-jump traces, включая отпускание вне ленты,
  pointercancel/lostcapture и границы. Проверить устаревшие ответы,
  достижение нужной даты, фокус и long tasks > 50 мс.
  Физические trackpad/touch/Ctrl+wheel оставить в R5.
- Для Edge собрать fast/slow diagnostic samples с тем же readiness и раздельными
  ready-panels/startup-overlap cohorts. Сопоставить RAF, native focus/visibility,
  bootstrap, decode и renderer tasks. Не смешивать traces с latency samples.
- Ограничить исследование одним отдельным диагностическим этапом. Если прежний
  хвост не воспроизводится, записать окружение, команды и результат
  INCONCLUSIVE; дальнейший объём и допустимость риска вынести на решение,
  не объявлять проблему исправленной и не повышать пороги.

**Приёмка:** разобранные профили взаимодействий, нет возврата к старой дате;
отклонения от guide объяснены либо устранены с regression.
Для изменённого cold path — 10 cold, 30 warm и return samples на оба dataset:
cold p95 < 300 мс, warm/return p95 < 100 мс; read p95 < 50 мс.
Не повторять eager/lazy эксперимент без нового основания.

## R4. Настоящие обложки и рост storage

**Вход от пользователя:** разрешённые локальные JPEG/PNG и manifest согласия.
Поддержка permitted manifest уже есть в `scripts/pulse-artwork-fixture.mjs`;
не создавать второй формат. До передачи файлов проверить существующие
опции harness и путь локального хранения; private файлы/пути/traces не коммитить.

- Подобрать разные bytes/resolutions/aspect ratios и сценарии отсутствия/
  повреждения. В packaged UI измерить HTTP transfer и browser decode отдельно;
  проверить видимость названия/статистики при ошибке изображения.
- Выполнить first-copy/existing/missing, checkpoint/final/retry с permitted
  originals, сверяя immutable hash и отсутствие лишних публикаций.
  Для ingest измерить median/p95/max и overlapping catalog read p95 < 50 мс;
  UI-порог 300 мс к ACK не применять.
- Дополнить actual audio → recorder → HTTP → SQLite прогон обложками.
  Записать raw/index, sampled WAL/SHM, архивы и staging до/после/retry/restart.
  Сопоставить с существующими 30/365-дневными моделями; короткий actual прогон
  не выдавать за год наблюдений, samples WAL — за peak.
- Thumbnail добавлять только при доказанном transfer/decode bottleneck,
  сохраняя оригинал и отдельную приёмку производного изображения.

**Приёмка:** воспроизводимый artwork/storage отчёт, точные ledger/day/album
суммы, bounded staging после R2. Без originals пункт остаётся NOT RUN.
Нативную/image/GPU память не подменять JS heap; полный memory повтор нужен
только при релевантном изменении layout/cache/lifetime или image pipeline.

## R5. Installed/manual — совместно с оператором

Использовать существующий
[единый checklist](../verification/pulse-p1.md#ручная-приёмка-установленного-приложения),
не заводить конкурирующую таблицу результатов.

- Согласовать установку и изолированный тестовый профиль. Записать SHA/dirty,
  executable/app.asar hashes, версию, Windows, DPI/zoom и устройства ввода.
- Пройти режимы, focus/scroll/Escape, playback/queue, low/portrait/fullscreen,
  темы/accent, ошибки и длинные имена; проверить общие player controls.
- На физических устройствах пройти trackpad/touch/Ctrl+wheel. Нет устройства —
  NOT RUN и отдельное решение о доступности приёмки, не автоматический PASS.
- Дефекты исправлять узко, с регрессией; после изменения пересобрать приложение
  и повторить затронутые ручные сценарии с новой идентичностью artifact.

**Приёмка:** заполненный оператором checklist и соблюдение композиции §5
финализации. Packaged automation не заменяет установленное приложение.

## R6. Финальный gate и передача

После последнего исходного изменения:

```sh
npm test
npm run build
npm run lint
npm run format:check
npm run test:e2e
git diff --check
```

`test:e2e` — полный Chrome + Edge без фильтров, skip и увеличения timeout ради
зелёного результата. Для R1–R2 дополнительно:
`npm run test:pulse:publication`, `npm run test:pulse:process`,
`npm run test:pulse:desktop`, `npm run benchmark:pulse:ingest`.
UI/ingest evidence повторять по затронутым сценариям на финальном artifact.
Если затронуты recorder/delivery/sleep/playback — заново определить и выполнить
релевантную P0-приёмку; физический sleep запускает только оператор.

Согласовать целевую интеграцию с `main`; результаты предшествующей ветки
не переносить автоматически на результат интеграции. После разрешённого push
получить CI на окончательном SHA; старый success не закрывает новый gate.
Для каждого результата хранить команду, exit/status, версию, hashes, окружение,
raw evidence и ограничения. Незавершённые проверки — INCONCLUSIVE/NOT RUN.

Новые результаты писать в `verification/pulse-p1-stage5.md` при выполнении,
не создавать журнал с вымышленными PASS заранее. В финализации обновлять
чекбоксы только по принятому evidence, сохраняя ссылки на предыдущие журналы.
Если внешний ввод недоступен или остаточный риск не принят, gate остаётся открыт.
Завершение плана не означает разрешения на публикацию/релиз.
