# Технический аудит milestone 0.1

Дата среза: 18 сентября 2026 года.

## Статус milestone 0.1

**Milestone 0.1 технически закрыт 18 сентября 2026 года.** P0 устранил двойное закрытие по `Escape`, изолировал stateful Playwright-сценарии, восстановил валидный benchmark и синхронизировал release-документацию. P1 сделал явными HTTP error semantics и лимит очереди, устранил N+1 при выдаче треков, оптимизировал тяжёлые facets, добавил безопасное обслуживание SQLite и CI quality gate.

P2 выполняется небольшими срезами без изменения внешнего поведения. Закрыты P2.1–P2.2 (client panels, dialogs и CSS boundaries), repository/migrations, worker/SSE/persisted-data и scanner-срезы P2.3, граница orchestration файловых операций, а также P2.4 — общие route/client response contracts и узкие MusicBrainz DTO. Следующая работа — измерения и настройки сканирования; она не является условием закрытия 0.1.

## Краткий вывод

Harbor Player — законченный первый milestone, а не прототип. Основные пользовательские потоки — подключение локальной коллекции, фильтрация, воспроизведение, перенос и удаление с восстановлением, пакетная запись тегов, обложки, MusicBrainz и Windows desktop shell — имеют защитные механизмы и широкую автоматизированную проверку.

Критических признаков риска немедленной потери музыки в текущем срезе не обнаружено. Полная переработка архитектуры не требуется: client/server/shared/desktop уже разделены, а дальнейшая декомпозиция должна сохранять проверенные границы безопасных файловых операций.

## Что уже сделано хорошо

### Сохранность файлов

- Запись тегов изолирована от основного процесса; разрешение записи зависит от проверки конкретной версии writer-библиотеки.
- Переносы и изменение тегов используют staging, fingerprint, резервные копии, flush и повторную проверку состояния исходника.
- Scanner не обходит symbolic links; пути повторно проверяются перед чтением и изменением.
- Прерванные jobs и operations переводятся в явное recovery-состояние при следующем запуске.

При дальнейшей декомпозиции `MusicService` эти свойства нужно сохранять характеристическими тестами, а не переносить логику большими блоками.

### Локальная безопасность

- Сервер слушает только `127.0.0.1` и проверяет `Host`, `Origin`, `Sec-Fetch-Site`, локальную cookie-сессию и CSRF для мутаций.
- Electron работает с `nodeIntegration: false`, `contextIsolation: true` и `sandbox: true`, ограничивает навигацию и проверяет отправителей IPC.
- Файловые действия и открытие в Проводнике отдельно проверяют принадлежность библиотеки.

Локальный API нельзя открывать в домашнюю сеть без отдельной модели аутентификации, ролей и угроз.

### Практичная тестовая база

114 unit/integration-тестов покрывают каталог, файловые операции, форматы тегов, обложки, MusicBrainz, фильтры, scanner и layout-утилиты. Playwright проверяет keyboard flow, responsive layout, полноэкранный режим, восстановление, перетаскивание обложек и групповое выделение; stateful fixtures разделены по браузеру и сценарию.

## Закрытые пункты milestone

### P0. [x] Качество доказательств и release-контур

- `ArtworkViewer` перехватывает `Escape` в capture-фазе, отменяет распространение и закрывает только viewer; режим обложки остаётся открыт.
- E2E server создаёт отдельные `Downloads`/`Collection`/`Tree` для Chrome/Edge и сценариев player, file operations, cover mode, folders и selection.
- Benchmark использует `folders`, заполняет `track_album_artists`, проверяет 100 000 треков, 10 000 альбомов и 1 000 треков выбранной папки. Обычный запуск пишет временный отчёт, а `npm run benchmark:baseline` обновляет версионируемый baseline.
- README и roadmap отражают NSIS/portable, beta updater и release workflow; clean-VM и первый подписанный stable честно остаются непроверенными.

### P1. [x] Надёжность API, каталога и CI

- `HttpError` разделяет ожидаемые `400`/`404`/`409`/`503` и внутренние `500`, сохраняя публичный формат `{ error }` без утечки внутреннего текста.
- `Catalog.tracks()` загружает форматы альбомов batch-запросом, а ответ ID делает ограничение 100 000 явным через `{ trackIds, total, truncated }`.
- Benchmark измеряет facets на 100k синтетической базе; оптимизированы `facetRelevance` и построение предков папок.
- Очистка SQLite удаляет только завершённые move/restore записи без recovery-пути; recovery-данные и операции с ошибками сохраняются.
- CI выполняет format, lint, typecheck, tag verification, unit/integration, browser smoke и desktop smoke; полный browser suite остаётся gate для push в `main`.

### P2. [x] Выполненные срезы декомпозиции

- `App` сокращён с 3743 до 2626 строк: вынесены shell/scroll hooks, bookmark control, virtual catalog views и library/genre panels при сохранении ownership верхнеуровневого состояния.
- Dialogs получили feature-границы и compatibility exports; `styles.css` стал manifest-entrypoint, а сохранённый cascade находится в `styles/base.css`.
- `Catalog.db` скрыт за узкими repository-методами; миграции v1–v6 вынесены в именованный транзакционный runner.
- Worker protocol различает `read` и `hash`, SSE описаны discriminated union, а persisted jobs/operations валидируются Zod при чтении.
- `LibraryScanner` владеет availability и scan-flow: incremental/force read, worker fallback, исключение symbolic links, ограниченный параллелизм, ошибки обхода и финализацию scan state.
- `OperationOrchestrator` стал узкой границей lifecycle файловых операций. `MusicService` сохраняет последовательную очередь, shutdown/cancellation и события, а его совместимые `preview`/`execute`/`retry`/`previewRestore` делегируют orchestration без изменения HTTP API или persisted payload.
- Общие Zod contracts проверяют успешные JSON route responses на серверной границе и используются клиентом при чтении ответа; URL, методы и публичный `{ error }` не изменены. MusicBrainz валидирует только используемые поля search/release/release-group/cover payload и cached JSON, не используя `any`.

## Приоритет 3: работа после milestone

### Сканирование

Сейчас сервер запускает полный обход библиотек при старте и каждые пять минут; метаданные неизменившихся файлов не читаются повторно, но traversal для больших или сетевых библиотек остаётся дорогим. В окно настроек следует добавить выбор частоты автосканирования, включая полное отключение автоматического скана.

Watcher может быть лишь подсказкой к scan, а не источником истины: Windows notifications теряются, а внешние диски и сетевые папки ведут себя неодинаково. До реализации нужны измерения на больших и недоступных библиотеках, а также явная persisted-настройка с безопасным default в пять минут.

### Размер клиентской сборки и наблюдаемость

Перед code splitting нужно измерить cold start. Наиболее вероятные кандидаты для lazy loading — большие dialogs, настройки и MusicBrainz workflow; основные панели и player следует оставить в стартовом bundle.

Для локального приложения достаточно ротационного локального журнала с версией приложения, job/operation ID, категорией ошибки и stack для внутренних сбоев. Пути к музыке и теги не должны автоматически уходить наружу.

## Рекомендуемый порядок следующего этапа

1. Повторить полный Playwright в чистом окружении и сохранить итоговый Chrome/Edge результат для следующей release-проверки.
2. Выполнить измерения на больших и недоступных библиотеках, затем спланировать persisted-настройку интервала автосканирования с безопасным default в пять минут.
3. Измерить cold start перед code splitting; после этого спланировать lazy loading больших dialogs, settings и MusicBrainz workflow, а также локальный ротационный журнал.

Milestone 0.1 не требует нового функционала для признания закрытым. Следующий этап должен развивать измеримость и сопровождаемость, сохраняя уже подтверждённую безопасность файловых операций.
